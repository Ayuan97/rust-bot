# 警报外部强提醒 — 需求与设计文档

> 状态:草案(Draft) · 最后更新:2026-06-07
> 范围:游戏内 Smart Alarm 触发后的「外部强提醒」(Bark 推送 + 阿里云语音电话),及其通知对象管理、触发规则、频率控制与静音机制。
> 关联代码:`notification.service.js`、`user-fcm-manager.js`、`global-manager.service.js`、`user-commands.js`、`user-event-monitor.js`、`settings.routes.js`

本文档是需求与设计的「事实来源」。实现细节(具体字段类型、接口签名)以代码为准;但功能规则、取舍与边界以本文档为准。推进时按 [§10 实施阶段](#10-实施阶段可勾选跟踪) 勾选。

---

## 1. 背景与目标

### 现状
游戏内 Smart Alarm(智能警报)触发 → Facepunch 经 FCM 推送 → 后端 `user-fcm-manager` 解析后 emit `alarm:triggered` → `global-manager` 转发并调用 `notificationService.notifyAlarm()`。目前**仅有 Bark 一个渠道**,且为全局环境变量配置(个人自用)。

### 目标
把警报升级为「能把人叫回来」的强提醒系统:
1. **多渠道**:Bark 推送 + 阿里云语音电话,可同时开启。
2. **能通知到队友**:不只付费本人,队友也能收到。
3. **收到后能方便地停止**:袭击会持续触发警报,必须有低成本的停止方式,避免轰炸。

### 非目标(本期不做,列为未来可选)
- 完整的团队 / 席位计费体系。
- AFK 精细判断(「在线但挂机」视同离线)。
- 接电话回执确认(谁接通了就不再呼叫谁)。
- 微信 / 短信等其他渠道。
- 警报事件(incident)的复杂状态机与自动收敛。

> 这些都在讨论中评估过,为控制复杂度本期砍掉,理由见 [§12 决策记录](#12-决策记录)。

## 2. 关键概念:两套「通知」不要混淆

项目里有两套都叫「通知」的东西,本文档只关注第二套,但必须和第一套划清界限:

| 维度 | 游戏内队伍播报 | 外部强提醒(本文档) |
|------|----------------|----------------------|
| 出口 | 游戏内队伍聊天 | Bark 推送 / 语音电话 |
| 对象 | 所有在线队友 | 本人 + 订阅的队友 |
| 前提 | 人在游戏里 | 人在游戏外也能触达 |
| 内容 | 货船/直升机/油井/队员等事件 | Smart Alarm 袭击警报 |
| 扰人/成本 | 低,免费 | 高,电话按次计费 |
| 配置入口 | `NotificationSettings.jsx` + `notification_settings` 表 | 本文档新增 |

**核心:外部强提醒的目的是「把游戏外的人叫回来」。** 这决定了它的触发规则(全队离线才启动)和静音逻辑(有人上线即停)。

---

## 3. 通知渠道

| 渠道 | 状态 | 配置层级 | 说明 |
|------|------|----------|------|
| Bark | 已有 | 平台级 env(现状) | iOS 强提醒,`critical` 可绕过静音;后续可演进为 per-user |
| 阿里云语音电话 | 新增 | 平台凭证走 env,号码 per-用户/订阅者 | `SingleCallByTts` + 已报备 TTS 模板 |

- 两个渠道**可同时开启**,用户与订阅者各自选择接收方式。
- 阿里云**平台凭证全局一份**(运营方账号):`AccessKey`、`TtsCode`(模板码)、签名、被叫显号 → 走 `.env`。不可能要求每个用户自带阿里云账号。
- **语音内容受限**:阿里云语音必须用预先报备审核的 TTS 模板(只能填变量槽,如 `设备${name}触发警报`),无法发任意文字。模板需运营方在阿里云控制台报备。

## 4. 通知对象与订阅

### 三类不重合的人群
- **付费账号(租户)**:一般一人,扫码配对 Rust+ 的那个,FCM 警报天然推给他。
- **游戏队伍**:Steam 层面的 N 人,系统里仅有 `SteamId + 游戏内昵称`,**不是平台用户**,够不到其手机。
- **真正要触达的人**:本人 + 部分队友。

### 身份模型:轻量订阅 + 代填(两种并存)
- **轻量订阅(自助)**:本人生成一个邀请链接分享给队友;队友打开后自助填写手机号 / Bark,订阅该服务器的警报。队友**不必注册完整付费账号**,且可**自助退订**。
- **代填**:本人也可直接替队友填写号码 / Bark。
- 订阅维度:绑定到「某用户(租户)+ 某服务器」的警报。

> 设计取舍见 [§12](#12-决策记录)。要点:轻量订阅让接收人能自己管理,代填覆盖「队友懒得点链接」的情况;两者互补。

## 5. 触发规则

- **外部强提醒仅在「全队离线」时启动。** 有人在线时,他在游戏里能看到队伍播报、能直接处理,此时不打电话,避免骚扰与话费浪费。
- 判定「全队是否在线」基于现有队伍在线状态追踪(`user-event-monitor` 的 `checkTeamInfo` / 队员在线数据)。
- 触发后:开始按 [§6 频率](#6-频率控制) 发送 Bark + 电话,直到 [§7 静音](#7-静音机制停止通知) 条件满足。
- **暂不区分 AFK**:在线但挂机的人当前视为「在线」(缺口已知,见非目标)。

---

## 6. 频率控制

- **可配置**:半小时内最多通知 **N** 次。
- **默认建议**:`2 次 / 半小时`(≈每 15 分钟一轮)。兼顾「持续叫人」与「话费可控」。
- **性质**:N 是**频率上限(控制密度)**,不是总量。无人响应、无人手动关时,会**跨窗口持续发送,直到有人上线或被手动静音**。
- **没有自动硬上限**:不做「发满就自动彻底停」。兜底依靠「保守的默认低频 + 手动关闭 + 有人上线」。
  - 风险:Smart Alarm 误触发 + 本人恰好长期离线时,会按低频持续呼叫(每通计费)。通过把 N 默认设小来软性控制,用户可调。

## 7. 静音机制(停止通知)

### 三个静音入口(满足任一即停)
1. **游戏内命令 `!关闭通知`** → 静音 **6 小时**,到期自动恢复。
2. **网站点击「关闭通知」** → 时长档位 **30 分钟 / 2 小时 / 6 小时**(默认 6h)+ **「立即恢复」** 按钮。
3. **有队友上线**(离线 → 在线的状态变化)→ 自动停止当前这轮通知。

> 入口 1 给「能上线发命令的人」用,入口 2 给「上不了线的本人」用,入口 3 全自动。三者覆盖所有情况。

### 静音语义(钉死)
- **只掐外部强提醒(电话 + Bark);游戏内队伍播报照常**——袭击时「X 区有人」是有用的战术情报,不一起关。
- **静音期间 Smart Alarm 照常监控、警报照常记录**(网站可见这段发生了什么),只是**不外呼**。
- **全队 / 整服生效**(不只发命令的那个人),语义是「这次别再往外打电话吵人了」。
- **权限**:第一版**任何队友都能发** `!关闭通知`(能上线发命令的本就是在处理的人)。未来要防滥用再收紧到队长。

### 反馈闭环(必须有)
- 发 `!关闭通知` → 游戏内队伍聊天回执:`已关闭外部警报 6 小时,将于 21:30 恢复`。
- 网站静音后 → UI 显示:`已静音,剩余 05:23 [立即恢复]`。

## 9. 数据模型(概念,待实现核实)

以下为**概念实体**,具体表名 / 字段 / 类型在实现阶段对齐 `users.id`、`servers.id` 后确定(见 [§11 待确认](#11-待确认--开放问题)):

- **用户通知偏好**(per user):渠道开关、本人号码、频率 N、默认静音档。
- **警报订阅者**(per user + server):号码 / Bark、来源(自助 / 代填)、退订状态。
- **静音状态**(per server / 租户):是否静音、到期时间、触发来源(命令 / 网站 / 上线)。
- (可选)**通知发送日志 / incident 记录**:用于网站展示「这段时间发生了什么」与排查。

> 待定:是否复用现有 `notification_settings`(JSON)还是新建表。倾向新建独立表(号码是 PII、语义不同),最终在实现阶段定。

## 10. 实施阶段(可勾选跟踪)

每个阶段附「完成标准」,便于验证推进。

- [ ] **阶段一:阿里云语音渠道接入(与 Bark 双通道)+ 本人号码配置**
  - 完成标准:配好 env 与本人号码后,模拟一次 `alarm:triggered` 能同时收到 Bark 与电话。
- [ ] **阶段二:通知对象 — 订阅链接 + 代填 + 退订**
  - 完成标准:能生成邀请链接,队友自助填号成功订阅;本人能代填;订阅者能退订;警报按订阅列表群发。
- [ ] **阶段三:触发规则(全队离线判断)+ 频率控制**
  - 完成标准:全队在线时不外呼;全队离线时按「N 次/半小时」发送,频率符合配置。
- [ ] **阶段四:静音机制(`!关闭通知` 命令 + 网站开关 + 上线自动停 + 反馈回执)**
  - 完成标准:三个入口都能静音并按时恢复;静音只掐外呼、游戏内播报照常;静音/恢复都有回执。
- [ ] **阶段五:前端 — 配置 UI(渠道 / 号码 / 频率 / 静音档)+ 订阅页**
  - 完成标准:遵循战术遥测设计系统;本人能配齐所有项;订阅页可用。
- [ ] **阶段六:联调与默认值校准**
  - 完成标准:端到端走通一次真实袭击场景;校准默认 N 与静音档。

## 11. 待确认 / 开放问题

### 技术核实(实现前确认,避免返工)
- `users.id` / `servers.id` 的类型(INT 还是 UUID/VARCHAR)→ 决定所有新表外键与 `userId` 字段。
- FCM `alarm:triggered` 实际携带的字段(`userId` / `serverId` / `entityId` / `entityName` / `message`)→ 决定语音模板变量与归属。
- 阿里云 `@alicloud/pop-core` 在本项目 Node 20 ESM 下的导入方式。
- (若将来做接电话确认)阿里云 `SingleCallByTts` 的「是否接听」回执机制(MNS 队列 / 回调)。
- 现有 `notification.service.js` 中 `notifyAlarm` 的 payload 字段名修正(`deviceName` vs `entityName` 不一致,已知,实现时一并修)。

### 产品开放项(可后续迭代)
- 网站静音是否保留档位 vs 固定 6h。
- `!关闭通知` 是否未来限定队长。
- 是否需要「通知发送日志」展示页。
- 是否补 AFK 判断 / 接电话确认 / 微信渠道。

## 12. 决策记录

记录关键取舍**及其理由**,便于后续回顾,避免反复讨论。

| 决策 | 选择 | 理由 |
|------|------|------|
| 渠道 | Bark + 阿里云语音,双通道可都开 | 国内号码用阿里云,与现有支付宝/微信支付同生态;Bark 保留作双保险 |
| 阿里云凭证 | 平台级 env 全局一份 | 不可能要求每个用户自带阿里云企业账号 |
| 队友身份 | 轻量订阅(自助链接)+ 代填,不强制注册 | 降低门槛;让接收人能自助退订/被动接收,为静音体验打基础 |
| 触发条件 | 全队离线才启动外部强提醒 | 强提醒的目的是叫醒不在的人;在线时打电话是骚扰 + 浪费话费 |
| 频率 | 频率上限(密度),无自动硬上限 | 用保守默认低频 + 手动关 + 有人上线兜底,比加状态机简单 |
| 静音范围 | 只掐外呼,游戏内播报照常 | 游戏内播报不扰人不花钱,且是有用的战术情报 |
| 静音生效域 | 全队/整服 | 语义是「这次别再往外打电话」,而非个人免打扰 |
| 静音权限 | 第一版任何队友可发命令 | 能上线发命令的本就是在处理的人;防滥用留到未来 |
| 砍掉的复杂度 | incident 状态机 / 接电话回执 / AFK 细分 | 控制本期复杂度,均列为未来可选 |
